docker compose --env-file .env/config.env up -d web
docker compose --env-file .env/config.env restart web

## Подготовка баз данных

```bash
./containers up --build -d web
```

При запуске PostgreSQL создаёт основную БД из `POSTGRES_DB` на пустом томе.
После проверки готовности PostgreSQL сервис `prepare-test-db` создаёт БД
из `POSTGRES_TEST_DB`, если её ещё нет. Затем `migrate` применяет общие
миграции к обеим БД, и только после его успеха запускается `web`.
Все параметры берутся из `.env/config.env`; имена основной и тестовой БД
должны отличаться. Тестовая БД принадлежит пользователю `POSTGRES_USER`.

Подготовка работает и при существующем томе: отсутствующая тестовая БД
создаётся, существующие базы и данные сохраняются. Ошибка подключения,
создания БД или миграции останавливает цепочку запуска приложения.
Интеграционные тесты очищают свои данные только в выделенной тестовой БД.

Ручное повторное применение миграций вместе с подготовкой тестовой БД:

```bash
./containers run --rm migrate
```

## Фиксация изменений PostgreSQL

Режим задаётся в `.env/config.env`:

```dotenv
POSTGRES_SYNCHRONOUS_COMMIT=off
```

Для этого тестового задания выбран асинхронный COMMIT: PostgreSQL подтверждает
транзакцию до завершения записи её WAL на диск. Проверки баланса, транзакции
и блокировки строк продолжают работать, `fsync` остаётся включённым.
При аварии PostgreSQL, ОС или потере питания последние подтверждённые операции
могут потеряться. Нагрузочный тест на исправной инфраструктуре не проверяет
сохранность таких операций после аварии.

Чтобы ждать сохранения WAL перед подтверждением, установить значение `on`.
Если переменная отсутствует, Compose также использует `on`. После изменения
применить конфигурацию контейнера, сохранив существующий том данных:

```bash
./containers up -d --wait postgres
```
